2. Reusable vector-store contract — audit faktycznego przypiętego kodu

kulai-vector-store 0.1.0:
- VectorRecord(id: str, vector: EmbeddingVector, metadata: dict[str, JsonValue]).
- VectorUpsertRequest(records: tuple[VectorRecord, ...], namespace: str | None).
- Namespace jest częścią requestu, nie recordu.
- Records batch nie może być pusty; IDs muszą być unikalne; dimensions spójne.
- VectorUpsertResult(store_id, ids, upserted_count) potwierdza ordered IDs/count.
- VectorStore jest structural Protocol: store_id, capabilities, async upsert,
  async search, async delete.
- upsert(*, store, request) rewaliduje dane, capabilities, namespace, metadata,
  backend identity oraz ordered response IDs/count.
- VectorRecord/requests są frozen/strict, extra=forbid. Metadata jest JSON-safe,
  finite dla liczb; EmbeddingVector zapewnia niepusty, finite vector.
- Error types obejmują Validation/Unsupported/Provider/Unavailable/ResponseError.
  Reusable service ukrywa raw exceptions; host dodatkowo udostępnia stały public error.

kulai-vector-store-pgvector 0.1.0:
- PgVectorStore(*, db: AsyncSession, config: PgVectorStoreConfig).
- Config(dimension: positive int, metric=VectorMetric.COSINE).
- Store reużywa istniejący reusable ORM model kulai_vector_records.
- upsert używa PostgreSQL INSERT ... ON CONFLICT(namespace_key, record_id)
  DO UPDATE dla embedding, metadata_json i updated_at; execute + flush.
- Nie wywołuje commit ani rollback.
- namespace=None mapuje się na pusty namespace_key; host zawsze używa exact namespace.
- Adapter sprawdza request dimension względem swojej konfiguracji przed SQL.
- ORM registration wiąże model z jednym fixed dimension na proces.
- delete jest namespace-scoped; execute + flush, missing IDs są idempotentne.
- search bierze gotowy query vector, top_k, namespace i EQ/IN filters (AND).
  Obsługuje metric COSINE/DOT_PRODUCT/EUCLIDEAN wybrany w config, higher-is-better
  scores i uporządkowane wyniki. Search/delete odczytano podczas audytu,
  lecz TASK 5B nie dodaje ani nie uruchamia retrieval/search/delete flow.
- Store nie owns DB lifecycle, engine, migrations ani transaction boundaries.

Contract wystarczył. Nie zmieniono vendor, schema ani migracji.
Host pyproject deklaruje teraz jawne deps kulai-vector-store oraz
kulai-vector-store-pgvector. Reusable packages były już zainstalowane.
Odświeżono editable metadata kulai-memory w obu SDK bez instalowania nowych
runtime packages (--no-deps -e backend).

6. Indexing service i nowe pliki

application/MemoryIndexingService:
- __init__(provider: EmbeddingProvider, expected_dimension: int | None).
- prepare(memory: Memory) -> VectorUpsertRequest.
- upsert(store: VectorStore, request: VectorUpsertRequest) -> VectorUpsertResult.
- MemoryIndexingError ma stały safe message i suppressed exception context.
- Service przyjmuje gotową canonical Memory; nie czyta DB i nie mutuje Memory.
- Nie tworzy providerów/store, nie zamyka ich, nie owns commit/rollback.
- Używa kulai_embeddings.embed i kulai_vector_store.upsert bez kopiowania reusable logic.
- Application core nie importuje Ollama concrete, PgVectorStore, SQLAlchemy,
  FastAPI, PySide6 ani transport adapters.

Host indexing_persistence:
- index_memory(memory, service, session_factory) przygotowuje vector PRZED
  otwarciem nowej write session.
- save_prepared_memory_vector(service, request, session_factory) zapisuje
  przygotowany request przez reusable PgVectorStore i owns commit/rollback.
- Returned result następuje dopiero po successful COMMIT i zamknięciu session.
- Failure zwraca safe MemoryIndexingError, bez vector/content/SQL payload.

7. Transaction boundaries

1. Canonical Memory read odbywa się w osobnej session.
2. Read transaction zostaje zakończona, session zamknięta, Memory detached.
3. prepare wykonuje embedding bez otwartej vector write session.
4. Host otwiera nową AsyncSession i session.begin() dopiero po prepare.
5. PgVectorStore wykonuje execute/flush.
6. Host transaction context wykonuje commit na success, rollback na failure.
7. Session jest zamykana przed zwróceniem wyniku.

Integration spies potwierdziły engine.pool.checkedout() == 0 przy embedding
zarówno fake providerem, jak i REAL Ollama clientem.
Unit test potwierdza kolejność embed -> session.open -> begin -> upsert -> commit
-> session.close, oraz rollback po commit failure.
Service nie może zamknąć obcej read transaction: caller ma przekazać detached
Memory po zamknięciu read session; contract jest jawnie opisany w docstring/README.
