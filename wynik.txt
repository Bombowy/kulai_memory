4. PostgreSQL atomic transaction
Host helper:
  kulai_memory.deletion_persistence.delete_memory(
    memory_id=UUID,
    session_factory=...
  )
Otwiera jedną AsyncSession i jeden session.begin().
PostgresMemoryRepository oraz PgVectorStore otrzymują tę samą session.
Kolejność:
  DELETE canonical Memory RETURNING id
  reusable vector delete
  caller-owned COMMIT
Repository i store nie ukrywają własnego commit.
Wynik hosta jest zwracany dopiero po wyjściu z udanego transaction context.
Błąd przed skutecznym COMMIT powoduje rollback obu zmian.
Cancellation propaguje jako asyncio.CancelledError i zamyka transaction/session.

5. Idempotent delete
Przypadki:
  Memory present, vector present -> memory_deleted=true, vector_deleted_count=1
  Memory present, vector absent  -> memory_deleted=true, vector_deleted_count=0
  Memory absent, vector present  -> memory_deleted=false, vector_deleted_count=1
  Memory absent, vector absent   -> memory_deleted=false, vector_deleted_count=0
Powtórzenie zakończonego delete zwraca false/0 bez błędu.
Nieistniejąca Memory nie blokuje cleanup orphan vector tej samej identity.

To hard deletion canonical row, również stored ingestion_id.
Nie dodano tombstone ani zmiany schematu/idempotency ingestion.
