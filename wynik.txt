20. Exact TASK 5B plan — zaprojektowano, NIE wdrożono

Cel następnego, osobno autoryzowanego taska:
canonical Memory -> document embedding -> VectorRecord -> durable vector upsert.
Memory pozostaje źródłem prawdy.

Identity:
namespace = kulai_memory.memories.v1
record_id = str(Memory.id)

Metadata minimum, JSON-safe:
- source_memory_id: str(Memory.id);
- embedding_provider_id: response.provider_id, obecnie ollama;
- embedding_model_tag: exact verified tag bge-m3:567m-fp16;
- embedding_dimension: response.dimension, obecnie 1024;
- embedding_model_digest: lokalnie zweryfikowany digest, jeśli dostępny.

Flow:
1. Jawny caller wskazuje Memory do indeksowania. Read Memory.content przez
   istniejący Memory service/repository, bez zmiany canonical Memory.
2. Caller tworzy jeden reusable embedding provider dla całego operation/batch.
   Wykonuje embed poza długą DB write transaction, w jednym event loop.
3. Request: EmbeddingRequest(inputs=(Memory.content,)), bez model_hint i purpose.
   Document oznacza tu rolę indeksowanego tekstu. Obecny Ollama provider ma
   supported_purposes=(), więc purpose=DOCUMENT byłoby controlled unsupported
   error. Nie wolno go dodawać ani implementować własnych prompt prefixes.
4. Wykonuje neutralne embed oraz host dimension compatibility helper przed
   jakimkolwiek vector write. Nie stosuje override ani matematycznej zmiany vectora.
5. Buduje VectorRecord(id=record_id, vector=response.embeddings[0], metadata=...).
   Namespace należy do VectorUpsertRequest(namespace=..., records=(record,)).
6. Host caller tworzy PgVectorStore(db=AsyncSession,
   config=PgVectorStoreConfig(dimension=1024)) i wywołuje reusable upsert.
   Store execute/flush, caller session.commit; failure -> caller rollback.
7. Retry zachowuje namespace i record_id. Istniejące UNIQUE(namespace_key,
   record_id) oraz reusable upsert gwarantują jedną identity vector recordu.
   Ponowne indeksowanie tej identity aktualizuje vector/metadata, bez nowego Memory.
8. Caller zamyka provider. Nie dodaje w tym kroku retrieval, RAG ani background queue.

Plan testów 5B:
- fake embeddings: mapping Memory id -> record identity i metadata;
- dimension mismatch/invalid response: brak store call;
- retry upsert tej samej identity: jeden row i poprawne metadata;
- caller-owned commit/rollback oraz brak modyfikacji Memory;
- real embedding + PgVectorStore integration wyłącznie w OWNED TEMP DB
  z synthetic Memory, migration do istniejącego head i guarded cleanup;
- main DB tests nie pozostawiają fixtures; backup/doctor i write authorization
  są jawnym etapem przyszłego taska przed indeksowaniem danych użytkownika.

Plan nie tworzy schema migration. Obecne JSONB metadata wystarcza do
powyższych minimum fields. Natywny model/digest należy ponownie zweryfikować
przed przyszłym write zamiast ufać wyłącznie historycznej deklaracji w raporcie.
