3. Decyzje dotyczące sesji i threat model
Access: maksymalnie 1 godzina. Krótszy TTL zatwierdzony przy parowaniu pozostaje.
Refresh: maksymalnie 30 dni od wydania, z rotacją przy każdym odnowieniu.
Sesja: nieprzesuwalna absolute expiry 90 dni od pierwszego claim.
Nowe access/refresh są ograniczane datą końca sesji; odnowienia nie przesuwają jej.
Te wartości ograniczają czas użycia skradzionych bearer credentials, ale refresh
pozostaje silną capability. Nie jest to sender-constrained/device attestation.
Każdy sekret powstaje przez standardowy CSPRNG secrets.token_urlsafe(32).
Access i refresh mają oddzielne UUID i formaty. Refresh: krf1_ + 43 URL-safe znaki;
access zachowuje dotychczasowe 43 znaki. Standardowy SHA-256 z oddzielną przestrzenią
refresh; PostgreSQL przechowuje wyłącznie digests, nigdy plaintext sekretów.
Publiczne device/session/token UUID nie stanowią uwierzytelnienia.
Uprawnienia są dokładnie zatwierdzonymi actions. Odnowienie nie dodaje scopes,
nie zmienia urządzenia ani project. Project isolation nie jest implementowana.
Wzorzec reakcji na refresh replay przeanalizowano wg RFC 9700 §4.14.2; ten protokół
nie deklaruje kompletnej zgodności z OAuth.

4. Replay, revocation i transakcje
PostgresSessionStore rozszerza istniejący store/reader; nie powstaje drugi system
Bearer authentication. Runtime v3 nadal używa tego samego Authenticator i polityki.
Pierwszy claim zatwierdzonego parowania zapisuje access, session, refresh i claimed
w JEDNEJ transakcji. Rotacja konsumuje poprzedni refresh, unieważnia jego access,
wstawia oba nowe credentials i zwiększa generation, również w jednej transakcji.
Sekrety odpowiedzi są dostępne dopiero po commit.
Lock order odnowienia: global rate advisory -> device -> session -> refresh -> access.
Dotychczasowy pairing zachowuje rate -> pairing -> device; operacje sesji nie
próbują blokować pairing po zablokowaniu device/session. Współbieżność testowana
z dwoma osobnymi procesami i osobnymi transakcjami PostgreSQL.
Poprawnie udowodnione ponowne użycie consumed refresh unieważnia całą rodzinę
oraz wszystkie jej access tokens. Odmowa wraca PO commit, aby revocation nie była
cofnięta rollbackiem. Dwie równoczesne próby: jedna rotacja, druga replay i revoke.
Zły sekret/UUID/claim urządzenia nie cofa cudzej sesji i nie ujawnia jej istnienia.
Device REVOKED jest stanem terminalnym i odcina wszystkie access/refresh credentials,
również gdy session.revoked_at pozostaje NULL: sprawdzany jest trwały status device.
Session-linked access nie może użyć starej administracyjnej rotacji access-only,
aby odłączyć się od granic swojej rodziny. Historyczny access-only flow pozostaje.
Reader robi jeden spójny SELECT z device/token/session/refresh i odrzuca consumed,
revoked/absolute-expired rodziny. Brak DB sesji podczas operacji AI.
Błędy storage są sanitizowane; nie ma retry transakcji ani logowania parametrów.

6. Refresh API i permission boundary
Dokładny POST /api/security/refresh jest wąskim wyjątkiem przed Bearer auth,
wyłącznie SECURE + dotychczasowy zweryfikowany local transport/Host/peer.
Brak prefix bypass, GET, WS, query, Origin, proxy headers lub publicznego issuer.
Authorization: Refresh <credential>, JSON dokładnie session_id/device_id/refresh_id,
canonical lowercase UUID. Brak project/device claim headers, dodatkowych pól,
duplicate headers/JSON keys, redirect i body >4096 B.
Wspólny parser bounded_json służy pairing i refresh, bez duplikowania walidacji.
Sukces: device_id, token_id, access_token, expires_at, session_id, refresh_id,
refresh_credential, refresh_expires_at, session_expires_at. Cache-Control: no-store.
Refresh nigdy nie uruchamia Whisper/BGE/Qwen ani prywatnego dostępu do Memory.
Refresh format nie jest akceptowany jako Bearer do żadnej prywatnej trasy HTTP/WS.
401 renewal_required wymaga parowania. 429 retry_later oraz brak usługi/schema
503 unavailable deklarują request_applied:false. Storage/commit uncertainty daje
503 uncertain bez obietnicy rollbacku. Inne błędy są stałe i nie ujawniają sekretów.
Global persistent limit: 120 security requests/minute. Rotacja family nie częściej
niż min(30 s, access TTL/2); maksymalnie 4096 generations. To nie publiczny DDoS ingress.

7. Wynik niepewny i zerwanie sieci
Serwer nie zapisuje recoverable plaintext refresh/access, nie retransmituje wydania
i nie udaje idempotentnego odbioru nowego sekretu po utracie odpowiedzi.
Android zapisuje encrypted renewal intent PRZED wysłaniem. Nowy snapshot publikuje
po durable atomic replacement obu credentials. Utrata odpowiedzi po możliwym
wysłaniu, nieznany commit, timeout, malformed success lub błąd zapisu oznaczają
re-pair. Restart z intent nie wysyła starego refresh ponownie.
OkHttp ma retryOnConnectionFailure=false i wyłączone redirecty dla capability API.
Per-call EventListener oznacza requestHeadersStart. Udowodniony failure przed tym
punktem albo jawna odpowiedź not-applied pozwalają zachować stare credentials
oraz bounded recovery. Nieznana odpowiedź gateway nie jest dowodem not-applied.
Nie ma automatycznego replay NOTE/Memory write ani zmian ingestion IDs/idempotency.

8. Android
Encrypted ConnectionRecord v2 odczytuje v1, obejmuje access + session refresh +
intent i origin. Android Keystore AES-256-GCM, losowy IV, authenticated envelope.
Jedna AtomicFile w noBackupFilesDir: fd.sync, sync directory rename, readback
ciphertext przed publikacją. Brak zwykłych SharedPreferences/secrets w BuildConfig.
Manifest backup disabled i FLAG_SECURE zachowane; nie implementowano plaintext fallback.
IO/crypto poza UI thread. CredentialProvider.current jest atomic, nonblocking snapshot.
Jedna wspólna RequestAuthentication dla HTTP i WS; ViewModel nie weryfikuje tokenów.
Równoczesne callers łączą się w jedno odnowienie; timeout renew 12 s, wait 15 s.
Proactive refresh do 5 minut przed expiry, dla krótkich tokens do 1/4 pozostałego TTL.
Aktywne NOTE/voice ASK odraczają proactive rotation, z kontrolą co najwyżej co 5 s,
WYŁĄCZNIE do real expiry access. Nie ma przedłużania ważności ani zmian Voice v1.
Po zakończeniu głosu klient odnawia; expiry/revoke nadal może zamknąć stary WS.
Bezpieczna recovery po outage: 5/10/20/40/60 s, maksymalnie pięć automatic retries.
CHECK/RETRY daje kolejną jawną próbę; nowy proces przywraca bounded recovery episode.
Paired/Expired/Revoked/Unavailable zachowane; failed SECURE nigdy nie przełącza LOCAL_DEV.
Snapshot/record przypisane do konkretnego canonical server origin. HTTPS/WSS dla
zewnętrznego origin, normalna weryfikacja certyfikatów/hostname, brak downgrade.
Spóźniona odmowa starego access request nie odrzuca już opublikowanego successor.
Utrata klucza/ciphertext lub niepotwierdzony intent wymagają ponownego parowania.

14. Znane ograniczenia / wymagane ręczne operacje
Brak krytycznej blokady implementacji refresh w zatwierdzonym środowisku lokalnym.
Main SECURE pairing/renewal nie będzie działać do osobno autoryzowanej instalacji
security; LOCAL_DEV nadal działa. Sam opis procedury nie jest zgodą na DDL.
Nie ma publicznego ingress/TLS ani kryptograficznego proof-of-possession urządzenia.
Bearer theft umożliwia użycie ważnych credentials; rotation/replay ograniczają ryzyko,
ale nie zastępują TLS, zaufania VPS, ochrony OS i świadomego approval.
Ambiguous commit/delivery celowo wymaga re-pair i admin revoke orphan device.
Old refresh replay może odciąć również legalnego klienta; dlatego singleflight/no retry.
Offline recovery jest bounded; po wyczerpaniu automatycznych prób wymaga CHECK/RETRY
lub restartu. Po refresh/absolute expiry nie ma trwałego logowania.
Active WS nie otrzymuje nowych handshake headers. Voice deferral chroni normalny
proactive renew; actual expiry/revoke nadal kończy access i nie replayuje zapisu.
Directory sync na innych Android/filesystem może odmówić — fail closed; wymagane QA.
Zegary muszą być prawidłowe; błąd czasu może powodować wcześniejszą odmowę.
Retencja receipt/history i recovery po DB rewind wymagają osobnej jawnej procedury.
Restore starej DB może wskrzesić credentials; nie wolno automatycznie otworzyć ingress
bez revocation odtworzonych aktywnych sesji i dotkniętych legacy credentials.
Końcowy APK wymaga fizycznego smoke po ponownym podłączeniu telefonu.
Real-model/internet/gateway/physical reboot tests oznaczone NOT RUN/SKIP, nie PASS.
