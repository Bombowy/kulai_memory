3. Struktury PostgreSQL i kontrakt storage
PostgresSecurityStore implementuje istniejące SecurityReader/SecurityStore.
Borrowed async_sessionmaker; store nie tworzy ani nie zamyka cudzego engine.

public.kulai_security_devices:
- id UUID PRIMARY KEY, trwała tożsamość oddzielona od secret;
- status text: pending/trusted/revoked zgodnie z wartościami istniejącego enum;
- created_at timestamptz NOT NULL.

public.kulai_security_tokens:
- id UUID PRIMARY KEY, device_id UUID FK do devices, ON DELETE RESTRICT;
- digest text NOT NULL UNIQUE, CHECK dokładnego SHA-256 hex;
- issued_at/expires_at timestamptz NOT NULL, CHECK expires_at > issued_at;
- revoked_at nullable timestamptz, trwała revocation;
- actions text[] ograniczone do memory.read, memory.write, assistant.ask,
  assistant.speech_plan; niepusta tablica, max 4 elementy, bez NULL/nieznanych akcji;
- nullable project_id UUID; brak FK lub pozorowanej izolacji canonical Memory;
- indeks device_id do operacji dotyczących właściciela.

Nie dodano plaintext token column, metadata, logów tokenów ani publicznego issuera.
Sekrety generuje istniejący CredentialManager; SQL otrzymuje wyłącznie digest.
Przetrwanie po restarcie: DB jest jedynym źródłem trust/token/revocation, bez cache.
UUID, zaufanie, scopes, expiry i revoked_at odczytywane są przez odtworzony adapter.
PENDING nie może otrzymać tokenu; REVOKED nie można ponownie zaufać zgodnie z v1.
Per-device actions działają. Project scope jest trwały, lecz current global routes
odrzucają scoped tokens; nie udawano per-project/per-user izolacji danych.

4. Transakcje, wyścigi i błędy
Wszystkie zapisy kończą commit/rollback i close przed zwróceniem wyniku.
Lock order: device row -> token row, zawsze w tej kolejności.
Nie ma procesowych mutexów zastępujących blokady PostgreSQL.

create_token blokuje urządzenie i sprawdza TRUSTED w transakcji przed insert.
set_device_status blokuje urządzenie; terminalny REVOKED nie jest reaktywowany.
rotate_token blokuje właściciela i stary token, ponownie sprawdza aktywność,
zgodność device/actions/project/issued_at, revokes old i inserts successor atomowo.
Tylko jedna równoczesna rotacja starego tokenu kończy się sukcesem.
revoke_token jest idempotentne i stosuje ten sam lock order.
Kontrolowana jest także zgodność właściciela po założeniu blokad.

Revoke vs rotate: wyniki odpowiadają kolejności serializacji.
Jeśli revoke wygrywa pierwszy, rotate odmawia. Jeśli rotate wygrywa pierwszy,
następca może powstać przed revoke starego tokenu; stary token jest już revoked.
Nie deklaruje się, że revoke starego ID retroaktywnie odwołuje każdy następny ID.
Revoke całego urządzenia blokuje wszystkie jego credentials, również następcę.
Issue vs device revoke: issue może commitować wcześniej, ale token po końcowym
revoke urządzenia jest nieaktywny; issue po revoke nie jest dopuszczone.

Błędy driver/statement/commit/rollback/close/dispose są zastępowane SecurityError
z komunikatem authored, bez params/URL/digest/token w publicznej treści lub cause.
CancelledError zachowuje cancellation; lookup rollback zwalnia pool. Dispose jest
shielded/drained istniejącym helperem, nie duplikowano mechanizmu drain.
Brak automatycznych write retries po niepewnym commit.
Utrata połączenia w trakcie rzeczywistego COMMIT może oznaczać niepewny wynik
po stronie klienta. Nie obiecuje się cofnięcia już wykonanego commit; po reconnect
należy sprawdzić durable state. Testy błędów przed commit wykazały pełny rollback.

5. Weryfikacja schematu i backup/restore
Read-only validator sprawdza:
- obecność dokładnego zestawu trzech tabel, typy/nullability/defaults/length;
- dokładne definicje PK/UNIQUE/FK/CHECK, validation i brak deferrable;
- poprawny indeks device_id i security revision;
- brak extra security tables/columns, user triggers oraz RLS.
Partial/unknown/incompatible schema fail-closed, bez udawania poprawnego storage.
PostgreSQL 18 NOT NULL constraints są uwzględnione w katalogowej kontroli.

run_database_doctor zachowuje wszystkie dotychczasowe strict checks i dodaje
security.schema. Brak wszystkich security tabel jest legalny dla starej lokalnej
alphy; schema obecna musi być w pełni poprawna. require_security=True wymaga jej
obecności i jest używane w produkcyjnym SECURE composition.

DatabaseSnapshot ma opcjonalne security=None, zgodne ze starymi konstruktorami
snapshotów i historycznymi dumpami. Zainstalowany pusty schemat jest innym stanem
niż brak schematu. SecuritySnapshot zawiera revision oraz hash/count wszystkich
pól device/token, również digest, scopes, expiry i revoked_at — bez wypisywania rows.
Ponieważ istniejąca backup_service porównuje pełne DatabaseSnapshot, actual restore
oraz source/archive revalidation obejmują teraz również trwałe security.
Zmiana revocation unieważnia uprzedni verified-source token.

Nowy schemat i pełny backup po jego instalacji przeszły rzeczywisty pg_dump/pg_restore.
Wykryto i poprawiono przed zakończeniem różnicę reprezentacji CHECK BETWEEN po restore:
migracja używa równoważnych jawnych bounds, więc exact doctor nie wymaga osłabienia.
Historyczne owned backupy 0002/0003/0004 nadal przechodzą istniejące guarded paths.
Zachowano tombstones, retired ingestion replay i backup/delete safety invariants.

8. Pomiar kosztu ponownej autoryzacji WS
Syntetyczny, rzeczywisty TCP/Uvicorn + PostgreSQL audio stream:
128 binary frames, 131 lookup (handshake + start + 128 frames + stop),
262 instrukcje adaptera: READ ONLY setup + coherent SELECT JOIN per lookup.
Przebiegi: 294.12 ms, 230.47 ms oraz 203.70 ms end-to-end; pool checkout=0.
Count pochodzi z SQLAlchemy statement events; driver BEGIN/COMMIT i pool pre-ping
housekeeping nie są zaliczone do tego licznika, lecz ich czas mieści się w pomiarze.
Native Android ma FRAME_SAMPLES=3200 przy 16 kHz: 200 ms / ok. 5 frames/s,
czyli typowo 10 instrukcji SQL adaptera/s plus housekeeping transakcji/pool.
Nie ma potrzeby cache optymalizacji dla zmierzonego lokalnego obciążenia.
Pozostawiono skuteczne sprawdzanie aktualnego stanu przy każdej ramce. Nie dodano
nieograniczonego cache ani opóźnienia revocation. Większy deployment wymaga osobnego
pomiaru; ewentualny bounded cache wymaga jawnego revocation budget i fresh STOP/RETRY.
Idle sockets i już admitted operacje mają dotychczasowe v1 semantics; brak push timer.

12. Ograniczenia, ryzyka i blokady
- Kod zweryfikowano, użytkownik polecił commit/push; main migration niewykonana.
  SECURE na obecnym main prawidłowo odmawia private access; LOCAL_DEV działa dalej.
- Brak pairing UI, QR, token issuance endpoints, discovery, TLS/WSS/LAN, internet,
  MCP, multi-user Memory i Memory Intelligence; nic z tego nie zostało rozpoczęte.
- Source DB jest zaufanym elementem systemu. To nie ochrona przed administratorem
  mogącym dowolnie modyfikować PG/backup; startup schema checks nie zastępują DB ACL.
- Stary bearer po revoke nie reaktywuje się przez transakcyjne race, ale posiadanie
  skradzionego nadal aktywnego bearer pozwala podszyć się pod jego urządzenie.
- Revocation sprawdzane przy każdej kolejnej ramce/request; admitted operacje nie
  są retroaktywnie cofane. Idle socket nie ma serwerowego push expiry/revocation.
- Device revoke jest terminalny w v1; politykę ponownego parowania trzeba zaprojektować
  jawnie w 4D.2B, zamiast automatycznie re-trustować odwołany UUID.
- COMMIT transport loss może dać niepewny wynik; brak automatic retries/false success.
- Manual przyszły restore starszego punktu czasu może cofnąć security state.
  Wznowienie po main recovery wymaga jawnej polityki revoke/rotation/verification;
  automatycznego restore main nie wdrażano. Aktualne restore verification i
  verified-source checks porównują także security i odrzucają stale/mismatched archive.
- Obecny pomiar to local synthetic stream, bez real models/physical device latency.
  Nie deklaruje się wyników load testu dużego deploymentu ani jakości mikrofonu/TTS.
- Brak blokady wymagającej dodatkowego input do implementacji. Jedynie aktywacja
  storage na main wymaga osobnego review/zgody na przygotowaną procedurę upgrade.
