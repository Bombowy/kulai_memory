2. Exact root cause
Dwa kroki składały się na odtworzone 500:
a) Windows PowerShell 5.1 może wysłać non-ASCII JSON string body w legacy
   encoding, jeżeli Content-Type nie określa charset. Dla "ó" powstaje payload,
   którego JSON parser nie może odczytać jako UTF-8.
b) Installed FastAPI routing importuje HTTPException ze starlette.exceptions
   i przy takim błędzie body parsing podnosi bazowe HTTPException(status_code=400).
   Nowy adapter importował HTTPException z fastapi, czyli subclass.
   except FastAPI.HTTPException nie łapał bazowego Starlette.HTTPException.
   Generic except Exception maskował expected client 400 jako internal 500.

Potwierdzono rzeczywiste installed API/source:
fastapi/routing.py importuje Starlette HTTPException i tworzy 400
"There was an error parsing the body".
To błąd HTTP exception mapping, nie canonical RAG.
TestClient z json= zawsze wysyłał poprawne UTF-8; poprzednie testy nie pokrywały
tej ścieżki błędnego encodingu i typu bazowego wyjątku.

Ważne: naprawa nie zgaduje kodowania i nie przepisuje query.
Invalid UTF-8 pozostaje invalid request: teraz safe 400.
Poprawne JSON UTF-8 działa jako FIRST request.
