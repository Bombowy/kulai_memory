3. Neutralny Security Core
Nowy pakiet kulai_memory.security, bez importów Memory/RAG, FastAPI, DB lub UI:
models.py — immutable Device, TokenRecord, Principal, IssuedCredential; walidacja
UUID, aware timestamps, akcji i okresu ważności; redacted reprezentacje sekretów.
configuration.py — SecurityMode LOCAL_DEV/SECURE, secure default, timeout auth.
storage.py — SecurityReader oraz SecurityStore; spójny lookup token/device,
atomowe create/revoke/rotate i statusy urządzeń; DenyAllSecurityReader.
authentication.py — Authenticator oraz zaufane lokalne CredentialManager API.
authorization.py — wspólna polityka action/project niezależna od transportu.
in_memory.py — referencyjny magazyn procesowy z atomowością także między wątkami.
__init__.py — neutralne publiczne API.

Device UUID, token UUID i sekret są rozdzielone. Urządzenia: PENDING, TRUSTED,
REVOKED. PENDING nie może otrzymać tokenu; REVOKED nie może zostać ponownie zaufane.
Sekret: secrets.token_urlsafe(32), 256 bitów losowej entropii, 43 znaki base64url.
Magazyn zachowuje tylko standardowy SHA-256 digest, bez tokenu plaintext.
Nie tworzono własnego algorytmu kryptograficznego ani podpisywania/JWT.
Ważność: issued_at <= now < expires_at. Domyślny TTL 1 h, maksymalny TTL 30 dni.
Authenticator weryfikuje digest, relację token/device, stan zaufania, revocation,
ważność i opcjonalny claimed device ID. Błędy magazynu również odmawiają dostępu.
Rotacja atomowo unieważnia stary token i tworzy jednego następcę tego samego
urządzenia, z niezmienionymi akcjami/projektem. Revoke tokenu jest idempotentne.
Nie ma publicznego endpointu wydawania/rotacji tokenów ani automatycznego bootstrap.
Magazyn pamięciowy jest jawnie nietrwały: restart usuwa jego stan. Nie pozorowano
trwałości. PostgreSQL adapter oraz jego migracja pozostają osobnym zadaniem.
Storage jest borrowed; właściciel adaptera, nie Memory runtime, odpowiada za close.

4. HTTP/WS enforcement
Nowy api/authentication.py zawiera pure ASGI middleware wspólne dla obu transportów.
Kontrola jest przed routingiem, redirect, walidacją body i uruchomieniem endpointu.
Po odmowie: zero tworzenia sesji/WAV, wywołań Whisper/BGE/Qwen, canonical read/write.
Autoryzacja:
- history/detail -> memory.read
- /ws/memory -> memory.write
- text/voice ASK -> assistant.ask
- speech-plan -> assistant.speech_plan
Nieznane prywatne operacje w SECURE są deny-by-default.

Authorization: Bearer <token> działa dla HTTP i natywnych WS z obsługą nagłówków.
X-Kulai-Device-ID jest opcjonalnym publicznym UUID; podany musi odpowiadać tokenowi.
Nie używa się IP klienta jako tożsamości. Token innego urządzenia z niezgodnym
claimed ID, untrusted/revoked device, expired/revoked/unknown token są odrzucane.
Odrzucane są malformed/duplicate Authorization i identity headers, credential
query keys (również zakodowane), wszystkie query WS oraz subprotocol credentials.
Cookie nie uwierzytelnia. Host/Origin i forwarded headers mają jawne odmowy.
Klienci browser wymagają przyszłej jawnej origin policy; obecne natywne nie mają Origin.

401: {"detail":"Authentication required."}, WWW-Authenticate: Bearer, no-store.
403: {"detail":"Access denied."}; brak informacji o Memory/stanie urządzenia.
WS odmowa przed accept: ASGI websocket.close 1008 -> rzeczywisty handshake HTTP 403.
Brak eventów sesji i prywatnego payloadu podczas odmowy.
Już przyjęty WS ponownie sprawdza token przed każdą prywatną ramką, w tym STOP/RETRY;
wygasanie/unieważnienie daje close 1008, bez nowych operacji prywatnych.

Podczas asynchronicznego lookup jeden watcher wykrywa disconnect. Bufor jest
ograniczony do 64 wiadomości i 64 KiB; po sukcesie dokładnie odtwarza wejście.
Domyślny timeout authentication: 5 s. Disconnect/cancellation anuluje i drenuje
lookup/watcher, zanim endpoint dostanie kontrolę. Nie ma polling ani sleep.
Dodano monitoring disconnect do /ws/memory podczas processing i save retry.
Whisper zachowuje shield/drain i dostęp do WAV do zakończenia; sieciowa inference
jest anulowana. Existing provider reuse i shutdown zamykają owned zasoby raz.
REST odpowiedzi i protokoły WS v1 (w tym IDs/retry/sequence) pozostają zgodne.

Host usuwa vendor RequestLoggingMiddleware i wyłącza jego fallback handlers przy
composition; vendor pozostaje nietknięty. Zostaje log transport/action/status oraz
istniejące bezpieczne stage/type/allowlisted code. Brak URL, headers, request ID
klienta, token/digest, body i private exception payload w server diagnostics.
Wyłączono debug tracebacks; nieobsłużony adapter error ma bezpieczny host fallback.
Kody błędów RAG spoza allowlisty logowane są wyłącznie jako none.

10. Ograniczenia i rozstrzygnięcia review
- To foundation, bez produkcyjnego pairing/persistent security storage. W zwykłym
  SECURE bez wstrzykniętego reader private requests są prawidłowo niedostępne.
- InMemorySecurityStore jest procesowy; nie współdzieli state między workerami,
  nie zachowuje rotation/revocation po restarcie. Nie ma hardcoded bootstrap secrets.
- Aktualna canonical Memory jest globalnym zasobem. Per-device actions są obsługiwane;
  project scope jest przygotowany w core, ale project-scoped credentials i client
  project headers są odrzucane przez obecne trasy. Nie ma pozornej row isolation.
- Sprawdzenie device ID wykrywa niezgodną deklarację właściciela, lecz bearer nie
  potwierdza fizycznego urządzenia. Nie zaimplementowano proof-of-possession.
- HTTP authorizes przy admission; WS przy handshake i kolejnych ramkach. Już
  dopuszczone operacje nie są retroaktywnie cofane. Idle WS nie ma push revocation
  ani timera zamykającego w chwili expiry; następna ramka jest kontrolowana.
- Canonical COMMIT wykonany przed disconnect indeksowania pozostaje trwały,
  zgodnie z istniejącym ingestion/idempotency. Nie dodano fałszywego rollback/Undo.
- Obecna faza dopuszcza cleartext wyłącznie lokalnie; TLS/WSS jest oddzielnym taskiem.
- ASGI middleware nie potrafi usuwać logów wygenerowanych wcześniej przez dowolny
  zewnętrzny proxy/server. Własny launcher ma bezpieczne flags; przyszły hosting
  musi zachować równoważną konfigurację loggerów, trusted proxies i bind.
- LOCAL_DEV jest świadomym anonymous dev exception dla loopback, nie uwierzytelnieniem
  opartym na IP. Browser access wymaga oddzielnej, jawnej origin policy.
- Konfiguracje desktop/DB/model, Canonical Memory, embeddings/namespace, migration
  graph, tombstones, ingestion IDs, protocol v1, TTS i backup invariants zachowane.
- Nie dodano zewnętrznych zależności, kont użytkowników, MCP ani Memory Intelligence.
