TASK 4A.1 — Fix real Windows microphone startup bug and error classification
Raport końcowy — 2026-10-05

1. Dokładny root cause TypeError

`MicrophoneRecorder.list_devices()` rozpoznawał parę input/output wyłącznie przez `isinstance(value, (tuple, list))`. Rzeczywisty `sounddevice.default.device` nie spełniał tego warunku, więc kod wykonywał `int(configured_default)` na całej parze. Obiekt nie obsługuje takiej konwersji i rzuca `TypeError`. Recorder opakowywał go jako `DesktopRecordingError`, po czym `DesktopController.startup()` błędnie przepakowywał ten publiczny błąd jako `DesktopDatabaseError`.

2. Rzeczywisty typ i charakter default.device

- Runtime sounddevice 0.5.6 zwraca obiekt typu `sounddevice._InputOutputPair`.
- Informacja o typie jest wyłącznie diagnostyczna; kod produkcyjny nie importuje ani nie sprawdza tej prywatnej klasy.
- Obiekt jest pair-like i reprezentuje się jako `[input, output]`.
- Nie jest instancją `list` ani `tuple`.
- Obsługuje indeksowanie: `[0]` to input, `[1]` to output.
- Bezpośrednie `int(pair)` kończy się `TypeError`.
- W raporcie nie zapisano nazw urządzeń ani innych prywatnych danych użytkownika.

3. Normalizacja default input

Dodano prywatne, provider-agnostic helpery w recorderze:

- scalar integer-like jest rozpoznawany przez `operator.index`;
- jeśli wartość nie jest scalarem, kod próbuje odczytać element `[0]`;
- element input jest normalizowany do nieujemnego integer device ID;
- output `[1]` nigdy nie uczestniczy w wyborze default input;
- kod nie zależy od nazwy ani implementacji prywatnej klasy sounddevice.

Odczyt listy urządzeń i host API nadal zgłasza kontrolowany `DesktopRecordingError`. Odczyt lub normalizacja samego optional defaultu jest best-effort i nie blokuje enumeracji.

4. Regression test pair-like

Dodano własny fake pair-like object:

- `repr(obj) == "[1, 3]"`;
- `obj[0] == 1`, `obj[1] == 3`;
- `isinstance(obj, (list, tuple)) == False`.

Test potwierdza, że `list_devices()` nie rzuca `TypeError`, input device 1 jest jedynym defaultem, a input-capable device 3 nie jest błędnie oznaczone na podstawie output side. Dodano też osobny test scalar default.

5. Brak poprawnego/default input

Niepoprawny obiekt defaultu oraz wartość `-1` nie przerywają enumeracji. Lista input devices jest zwracana normalnie, a wszystkie wpisy mają `is_default=False`.

6. Poprzednia błędna klasyfikacja exception

Po poprawnym db_doctor drugi szeroki blok `except Exception` zachowywał tylko `DesktopConfigurationError` i `DesktopDatabaseError`. Każdy inny błąd, w tym prawidłowo sklasyfikowany `DesktopRecordingError`, był mechanicznie zamieniany na `DesktopDatabaseError`. UI otrzymywał przez to fałszywy komunikat o niedostępnej bazie.

7. Nowa klasyfikacja startup errors

- Każdy istniejący `DesktopPublicError` zachowuje swój typ i safe public message.
- `DesktopRecordingError` pozostaje błędem mikrofonu.
- `DesktopConfigurationError` pozostaje błędem konfiguracji/CUDA.
- `DesktopDependencyError` pozostaje błędem zależności.
- Błąd doctor lub nieoczekiwany błąd engine/session setup jest klasyfikowany jako `DesktopDatabaseError`.
- Nieoczekiwany błąd providera lub innego niedatabazowego etapu staje się bazowym, bezpiecznym `DesktopPublicError`.
- Raw exception message nie trafia do UI.
- Cleanup częściowo utworzonych zasobów nadal jest wykonywany przed ponownym rzuceniem błędu.

UI pokazuje public message otrzymany ze startupu. Pomocniczy status ma neutralne `Startup failed`; nie zawiera już hardcodowanego `Database startup check failed` dla wszystkich klas błędów.
