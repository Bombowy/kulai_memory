4. Neutralny lifecycle contract
MemoryLifecycleService zależy od neutralnego MemoryMutationRepository
oraz reusable VectorStore. Nie importuje SQLAlchemy, PgVectorStore, Ollama,
FastAPI, Qt ani adapterów klienta.
MemoryLifecycleResult: canonical Memory + typed MemoryLifecycleStatus.
Statusy: EDITED, UNCHANGED, ARCHIVED, ALREADY_ARCHIVED, RESTORED, ALREADY_ACTIVE.
Host change_memory zwraca MemoryChangeResult z canonical wynikiem,
opcjonalnym wynikiem indexing i safe indexing_error_code.

EDIT:
- wspólny ingestion advisory lock, następnie canonical FOR UPDATE;
- walidacja active state oraz expected_revision;
- dokładnie niezmieniony content oznacza UNCHANGED, bez increment/delete;
- zmieniony content zwiększa revision o 1;
- content/revision update i vector DELETE w jednej transakcji;
- COMMIT i zamknięcie canonical session;
- dopiero potem embedding nowego exact contentu i krótki vector COMMIT;
- finalna metadata revision musi odpowiadać aktualnej canonical Memory.
ID, ingestion_id, created_at, source_kind, session_id i metadata pozostają.

ARCHIVE:
- archived_at ustawione raz na UTC timestamp;
- canonical Memory pozostaje, revision pozostaje;
- vector DELETE w tej samej transakcji;
- powtórzenie zachowuje pierwsze archived_at;
- zero embeddingów i zero tombstone creation;
- Recent Memory, retrieval, automatic reconciliation i oba backfill modes
  pomijają archiwum;
- replay ingestion nie przywraca Memory, kończy safe memory.archived.

RESTORE:
- archived_at=NULL w krótkiej canonical transakcji;
- COMMIT/session close przed embeddingiem;
- automatic ensure-indexed odtwarza vector dla tej samej treści/revision;
- powtórny RESTORE może naprawić missing vector;
- compatible existing vector nadal kosztuje zero embeddingów/upsertów.

5. Revision compatibility i races
Exact identity pozostaje:
namespace=kulai_memory.memories.v1
record_id=str(Memory.id)
Metadata zawiera source_memory_id, embedding_provider_id,
embedding_model_tag, embedding_dimension i revision.
Content ani arbitrary Memory metadata nie są kopiowane do vector metadata.
Revision musi być dodatnim int; bool/float/string są incompatible.
Retrieval wymaga active canonical Memory i exact matching revision.
Archived albo stale hit daje controlled error, bez cichego mieszania treści.
Canonical treść nadal pochodzi z memories table; ranking pozostaje zachowany.

Lock ordering:
- ingestion/edit/archive/restore/delete: ingestion advisory -> canonical row;
- lifecycle mutation/delete: canonical row -> vector;
- indexing: canonical row FOR UPDATE -> vector.
Nie wprowadzono process-local identity locka zamiast PostgreSQL locka.

Pre-check oraz finalny canonical FOR UPDATE sprawdzają active/revision.
Prepared embedding sprzed EDIT/ARCHIVE/DELETE nie może stworzyć stale vectora.
Real PG testy mutation-wins i index-wins PASS; drugi kierunek udowodnił
rzeczywiste oczekiwanie pg_stat_activity wait_event_type=Lock.
Dwa jednoczesne EDIT expected_revision=1: jeden wygrywa, drugi conflict;
revision kończy na 2, bez deadlocka. Test ma timeout.
Dotychczasowe delete/index/replay race regressions przechodzą.

6. Transakcje, failure i crash recovery
Embedding nie ma checked-out DB connection.
Memory edit/restore COMMIT jest wcześniejszy od Ollama requestu.
Vector/delete/commit failure w canonical transakcji cofa Memory change
oraz vector deletion razem. Cancellation w tej fazie również rollbackuje.
Po committed EDIT/RESTORE indexing failure nie cofa canonical state.
Result jawnie oznacza zapisany canonical change + indexing failure.
Cancellation po EDIT COMMIT pozostawia revision=2 i brak vectora;
startup reconciliation naprawia gap bez zmiany Memory fingerprintu.

Automatic reconciliation i backfill wybierają wyłącznie active Memory,
w dotychczasowym bounded deterministic ordering. Archive nie jest missing index.
Incompatible revision metadata jest reported, bez automatic overwrite.
Manual świadomy reindex nadal używa finalnego active/revision guardu.
Tombstone semantyka hard delete pozostaje; hard delete archiwum także
usuwa Memory/vector i zapisuje techniczny tombstone.
