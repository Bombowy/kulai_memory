2. Threat model i granice zaufania
Threat model zapisano w docs/LOCAL_ASSISTANT_TRANSPORT.md przed implementacją.
Granice: zaufany lokalny administrator CLI -> niezaufany klient -> ASGI ingress ->
application service -> transakcja PG -> chroniony storage Androida.
Publiczny UUID, nazwa, IP, USB ani znajomość identyfikatora sesji nie są dowodem.
Uwzględniono stolen invitation, podstawienie odbiorcy, replay, równoległe request/
claim/revoke, enumerację, limity/brute force, oversized/malformed input, logging,
backup export, utratę Keystore, origin substitution, redirects i błędy storage.
Administrator porównuje konkretną sesję, device UUID oraz pełny publiczny SHA-256
receiver verification code telefonu i CLI przed zatwierdzeniem.
Złodziej zaproszenia może zająć PENDING, ale nie otrzyma tokenu bez świadomego approval.
Wyczerpanie budżetu znanej sesji może spowodować odmowę prawowitemu użytkownikowi;
to ograniczenie dostępności, nie obejście zaufania. Nowe zaproszenie wymaga review.
CSPRNG secrets.token_urlsafe(32) / SecureRandom: 256 bitów. Standardowy SHA-256,
AES-GCM i platformowy Keystore. Brak własnych algorytmów kryptograficznych.

3. Przebieg protokołu
Administrator lokalnie tworzy zaproszenie z jawnymi permissions i TTL tokenu.
Invite TTL: 5 minut, jednorazowe związanie z odbiorcą.
Telefon tworzy niezależny receiver secret CSPRNG oraz publiczny registration UUID.
Najpierw zapisuje zaszyfrowany pending state, potem wysyła request.
Pierwszy request tworzy nowe server-owned device UUID i stan PENDING.
Wskazanie publicznego UUID nie rejestruje ani nie reaktywuje istniejącego urządzenia.
Dokładny retry request jest idempotentny i wymaga zaproszenia ORAZ tego samego receiver.
Inny receiver/client/label nie może podmienić istniejącego związania.
Po potwierdzeniu rejestracji Android usuwa invitation secret z zapisanego stanu.
Approval dotyczy konkretnego session/device/code; dopiero wtedy device = TRUSTED.
Claim wymaga receiver proof, niewygasłej sesji, approval i aktualnego TRUSTED.
W jednej transakcji zapisuje token digest i zużywa sesję. Tylko jeden claim wygrywa.
Token plaintext jest zwracany raz do telefonu, nie do CLI, DB, metadanych czy logów.
Telefon zapisuje cały credential encrypted/atomic przed publikacją snapshotu.
Cancel pending/approved jest kontrolowany i idempotentny; nie pozostawia zaufania.
Cancel claimed pozwala właścicielowi receiver proof unieważnić własne urządzenie.
Status ujawnia wyłącznie własną sesję po proof i uwzględnia revoke/expiry jej tokenu.

4. Odbiór jednorazowy i lifecycle tokenów — świadoma decyzja
Access TTL domyślnie 1 godzina, administrator może wybrać 1..86400 sekund.
Istniejący neutralny CredentialManager zachowuje poprzednie bounded TTL/rotation.
W tym zadaniu brak refresh credential i publicznego refresh/rotate endpointu.
Nie zwiększono uprawnień przy wydaniu ani rotacji. Project scope pozostaje None;
nie pozorujemy izolacji projektów lub multi-user canonical Memory.
Wygasły/revoked token nie daje dostępu; device revoke odcina wszystkie jego tokeny.
Przed claim Android zapisuje marker claiming. Po niepewnym commit, utracie odpowiedzi
lub nieudanym zapisie tokenu nie odzyskuje sekretu przez replay. Wymaga nowego pairing
oraz administrator revoke osieroconego urządzenia. Brak plaintext replay storage.
Po restarcie zapisany token jest publikowany dopiero po sprawdzeniu własnej sesji.
Czasowa utrata połączenia daje Unavailable, pozwala ponowić sprawdzenie istniejącego,
nadal ważnego stanu; nigdy nie przedłuża TTL ani automatycznie nie włącza LOCAL_DEV.
Clock error telefonu może odmówić dostępu wcześniej; czas serwera rozstrzyga ważność.

5. Moduły backendu i transport
Pairing domain/application: backend/src/kulai_memory/pairing/domain.py.
Port PairingStore jest niezależny od FastAPI, Memory i RAG.
PostgresPairingStore rozszerza istniejący adapter i pożycza session factory;
nie tworzy drugiego production pool ani nie trzyma DB podczas AI.
Wspólną funkcję przygotowania CSPRNG credential wydzielono z istniejącego Managera,
bez duplikowania kryptografii, nowej zależności ani zmiany dotychczasowych TTL.
PostgresSecurityRuntime nadal zarządza jednym pool; pairing service istnieje tylko
po zweryfikowaniu v2. Poprawne historyczne v1 nadal obsługuje wcześniejsze bearer auth.
Brak/awaria security pozostaje fail-closed bez startupu AI i bez auto-DDL.

Jedyny pre-auth wyjątek: HTTP POST dokładnie na:
/api/pairing/request, /api/pairing/status, /api/pairing/claim, /api/pairing/cancel.
Wyłącznie SECURE, rzeczywisty loopback listener i peer, zgodny Host/listener port.
Brak browser Origin, proxy headers, query, suffix/prefix/WS/admin-route bypass.
Authorization: Pairing <secret>. Content-Type application/json, opcjonalnie UTF-8.
Manual parsing ogranicza body do 4096 B, odrzuca duplicate/unknown JSON fields,
duplicate headers i malformed UUID. Nie używa odbijających sekrety błędów walidacji.
Public errors są ogólne; poprawne payloady mają Cache-Control: no-store.
Disconnect watcher jest wspólny z authentication; anulowane work/watcher są drained.
Zwykłe prywatne HTTP/WS nadal używają tego samego Bearer enforcement i policy.
/health pozostaje publicznym liveness bez konfiguracji lub danych użytkownika.
Nie wystawiono CredentialManager jako anonimowego issuer ani publicznego admin API.

6. PostgreSQL, schema, transactions i limity
Nowy security head: kulai_security_0002, po kulai_security_0001.
Canonical head pozostaje kulai_memory_0004; istniejące migracje niezmienione.
Dodano public.kulai_security_pairings i public.kulai_security_pairing_rate.
Pairings: UUID, invite/receiver digests, public client/device UUIDs, label, state,
created/expires/approved timestamps, issued token UUID, permissions, TTL i attempts.
Rate: trwały singleton window_start/attempts. Nie ma plaintext secret columns.
FK/UNIQUE/CHECK/index są sprawdzane dokładnie przez strict doctor, także po restore.
Doctor odrzuca partial schema, dodatkowe pola/tabele, brak constraint/index, bad head,
triggers i RLS. Obsługuje absence, v1 i v2, bez udawania tabel w starym backupie.

Limity: 8 aktywnych sesji, 128 retained sesji, 8 failed proofs/session,
120 service calls/minute globalnie między procesami. Poll telefonu co 5 sekund.
Anonimowy transport nie tworzy zaproszeń, więc nie ma nieograniczonego create API.
Global advisory limiter -> session row -> device row -> token row.
Dotychczasowe credential writes zachowują device -> token order; brak odwrotnego cyklu.
Failed proof zapisuje counter i commit przed odmową; denial nie cofa jego budżetu.
Approve/claim ponownie sprawdzają expiry po blokadach. Claim i device revoke linearizują:
revoke pierwszy odmawia claim; claim pierwszy wydaje token, który revoke dezaktywuje.
Constraint/statement/commit failures robią rollback i bezpieczne wyjątki.
Nie obiecujemy cofnięcia commita przy zerwanym połączeniu w niepewnym momencie COMMIT.

CLI prune-expired --confirm zwalnia retained budget, usuwa tylko expired sessions
bez live trusted tokenu, revokes abandoned unclaimed devices. Zachowuje device/token
rekordy. Prune jest jawny, bez automatycznego maintenance i bez wykonania na main.

8. Android UI, credentials i ownership
Server Connection: canonical configurable origin, jawny LOCAL_DEV dla debug oraz
Not paired / Pairing / Paired / Expired / Revoked / Unavailable, safe errors,
Pair Device, oczekiwanie, comparison code, CHECK/RETRY, cancel, local unpair.
Przed skutecznym pairing/verify prywatny UI w SECURE jest zablokowany.
RequestAuthentication pozostaje wspólnym mechanizmem wszystkich HTTP i obu WS.
Po 401/WS refusal powiadamia connection controller, który weryfikuje własny stan;
spóźniona odmowa innego device UUID nie usuwa nowego credential.
HTTP 403 z braku danego scope nie jest automatycznym device revoke.
Server origin jest przypisany do credential i sprawdzany przed wysłaniem.
Remote URL wymaga HTTPS; debug HTTP wyłącznie loopback; paths/userinfo/query/fragment
są odrzucane, redirects i retry-on-connection-failure dla one-shot claim wyłączone.
Platform certificate i hostname verification pozostają aktywne.

AES-256-GCM / AndroidKeyStore key; losowy 96-bit IV i 128-bit tag, version AAD.
Jeden encrypted AtomicFile w noBackupFilesDir, nie plaintext SharedPreferences.
Manifest allowBackup=false pozostaje; noBackupFilesDir chroni także transfer.
UI secrets są remember, bez rememberSaveable/Bundle; FLAG_SECURE.
IO/Keystore poza main thread. CredentialProvider to AtomicReference snapshot,
thread-safe i nonblocking; expiry odcina snapshot. Nie ma nieograniczonego auth cache.
Whole-record atomic replacement i claim-intent chronią spójność po awarii/restart.
Jawny fd.sync propaguje błędy zapisu; read-after-write sprawdza rename, ponieważ
Android AtomicFile może samo logować błąd rename zamiast rzucać wyjątek.
Utrata klucza/decryption failure wymaga nowego pairing, bez plaintext/dev fallback.
Konfiguracja/recreate features zamyka stare controllery i transporty; zachowano
microphone permission oraz istniejący wspólny MicrophoneGate i feature shutdown.
Poprawiono systemBars/IME insets po teście fizycznym; nie dodano biblioteki UI/storage.
Local unpair zawsze usuwa secret; server cancel best-effort. Offline orphan revoke
wymaga CLI. Zmiana origin również usuwa lokalny credential; przed nią należy revoke/
unpair starego serwera, żeby nie zostawić dostępu po jego stronie.

14. Review, ograniczenia i blokady wdrożenia
Przeprowadzono self-review security/architecture, permission boundaries, exact ASGI
exception, lock order, durable deny counters, replay/rollback, cancellation/pool,
origin/redirect, encrypted persistence i backup/schema compatibility. Testy niezależnie
sprawdziły te granice; nie twierdzimy, że wykonano zewnętrzny audyt.
Main SECURE pairing pozostaje niedostępny dopóki użytkownik osobno nie zatwierdzi
pełnej procedury instalacji security. To zamierzona granica, nie auto-fallback.
Bearer i receiver capabilities nie są device attestation. Keystore key hardware
backing nie jest gwarantowane; compromised OS/local admin pozostają poza modelem.
Idle WS i już admitted operacje zachowują poprzednie v1 revocation semantics.
Rate limits mogą odmówić podczas przeciążenia; nie stanowią publicznego DDoS ingress.
Nie ma trwałego loginu poza ważnością tokenu ani refresh credential/recovery replay.
Pięć minut ogranicza registration/approval/claim; zużyta sesja zachowuje receiver
capability wyłącznie do własnego status/revoke do jawnego prune, także do pokazania
Expired/Revoked. Nie pozwala ona odzyskać, wydać ani przedłużyć tokenu.
Offline local removal/server change może pozostawić server-side orphan; explicit revoke.
UI pokazuje prywatny client shell po uwierzytelnieniu; szczegółowe scope denial
pozostaje w wspólnym backend policy (brak multi-project isolation).
Nie uruchomiono 0.0.0.0, LAN, VPS, TLS termination, proxy/tunelu, discovery, QR,
MCP, Multi-user Memory ani Memory Intelligence. Backend/DB/model endpoints prywatne.
